# InvestLab 레포 간 협업 규약

작성일: 2026-10-10 (KST)

상태: 3개 레포 설계를 위한 규약 초안. 구체적인 제한시간·배포 환경·도구 버전은 착수 시 확정한다. 기존 공개 API 명세의 정책은 유지하며 내부 AI 계약은 신규 작성 대상이다.

## 1. 책임과 기준 위치

### 1.1 팀 담당

| 이름 | 담당 | 현재 분담 상태 |
| --- | --- | --- |
| 송상진 | 백엔드, 명세·설계 문서, 인프라 | 백엔드 기능별 분담 미정 |
| 박진호 | 백엔드 | 백엔드 기능별 분담 미정 |
| 유광민 | AI | AI 구현·수집·RAG 담당 |

프론트 담당과 기술은 미정이다. 기능 담당은 이슈에서 정하고, 문서에서 인증·거래 등 백엔드 기능을 임의로 배정하지 않는다. 담당자는 구현·기준 유지 책임자이며 회의 설명과 CI 통과 후 자기 PR을 머지할 수 있다.

### 1.2 기준 위치·담당·검토

| 대상 | 기준 위치 | 책임 담당 | 변경 검토 |
| --- | --- | --- | --- |
| 공개 API 명세 | investlab-backend/contracts/public-api.yaml | 송상진 | 작성자 외 백엔드 담당, 향후 영향받는 프론트 담당 |
| 내부 AI API 명세 | investlab-ai/contracts/internal-ai-api.yaml | 송상진: 명세 관리 / 유광민: AI 구현 일치 | 작성자 외 백엔드·AI 영향 담당 |
| 전체 아키텍처·협업 규약·원본 명세 | investlab-backend/docs | 송상진 | 박진호 또는 유광민, 변경 영역에 따라 검토 |
| 인프라·통합 실행·배포 설정 | backend/infra 및 각 레포 CI·배포 파일 | 송상진 | 작성자 외 영향받는 담당 |
| 백엔드 구현·거래 DB 마이그레이션 | investlab-backend | 송상진·박진호 | 상대 백엔드 담당 |
| AI 구현·기업분석 DB 마이그레이션 | investlab-ai | 유광민 | 송상진 또는 박진호, AI 계약·검증 결과 포함 |
| 앱별 의존성 | 해당 앱 레포 | 백엔드: 송상진·박진호 / AI: 유광민 | 작성자 외 담당 |
| Secret·운영 환경 설정 | 레포별 배포 환경 | 송상진, AI 필요 설정은 유광민과 협의 | 값 공개 없이 적용·권한·교체 방식 검토 |

GitHub 계정명은 아직 받지 않았으므로 CODEOWNERS와 실제 권한 설정에는 실명 대신 계정명을 확인하여 반영한다. 관련 레포의 읽기·리뷰·머지 권한도 이 규칙을 수행할 수 있게 설정해야 한다.

여기서 계약은 URL, 요청·응답 필드, 타입, 필수 여부, 상태·오류, 인증, 동작 의미까지 포함한 약속이다. Java 엔티티·Python 모델·향후 프론트 타입을 동일한 소스 파일로 공유할 필요는 없다.

소비자는 제공자 레포의 특정 태그나 커밋에서 계약을 가져온다. 브랜치 최신 파일을 매번 가져오지 않는다. 별도 패키지 레지스트리 없이 시작할 수 있으며, 비공개 레포의 CI 접근은 최소 읽기 권한으로 설정한다. 생성 클라이언트·타입을 커밋한다면 생성 명령과 기준 계약 커밋을 함께 기록한다.

## 2. 공통 데이터 표현

| 항목 | 규칙 |
| --- | --- |
| 공개 경로 | 기존 /api/v1 계약 유지 |
| 내부 AI 경로 | /internal/v1을 제안. 실제 엔드포인트는 내부 계약 작성 때 확정 |
| 직렬화 | application/json, UTF-8, JSON 필드는 camelCase |
| ID | UUID 문자열. companyId, instrumentId, documentId의 발급 책임을 명시 |
| 금액·가격·수량·비율 | Decimal 문자열. Java BigDecimal·Python Decimal 사용, JS 부동소수점 계산으로 거래값을 확정하지 않음 |
| 수익률 | 퍼센트 단위. "0.2"는 0.2%이며 20%가 아님 |
| 시각 | ISO 8601 UTC(Z). 날짜 경계·초기화 일자는 Asia/Seoul |
| 날짜 | YYYY-MM-DD. 회계연도·분기·보고서 기간은 별도 필드 |
| 누락 | null, 필드 생략, 0의 의미를 구분. 시세·근거 부족을 0으로 대체하지 않음 |
| 상태 | 계약에 정의된 enum 사용. 추가 시 소비자의 미지 상태 처리를 검토 |
| 목록 | 기존 cursor·limit·nextCursor와 정렬 규칙 유지 |

재무 값은 단위·통화·기간·연결/별도 기준을 함께 전달한다. ROA·ROE 등 계산식과 분모 기준은 기존 P-07 제안의 승인 후 고정한다.

## 3. 공개 응답과 오류

기존 API 명세의 형식을 유지한다.

```json
{
  "data": {},
  "meta": { "requestId": "요청 식별자" }
}
```

```json
{
  "error": {
    "code": "DATA_UNAVAILABLE",
    "message": "데이터를 조회할 수 없습니다.",
    "details": []
  },
  "requestId": "요청 식별자"
}
```

빈 목록, 리소스 없음, 권한 거부, 가격 지연, 외부 장애를 구분한다. 기존 400/401/403/404/409/422/429/503 의미를 유지한다. 내부 AI 실패는 백엔드에서 공개 오류로 변환하며 내부 URL·스택·공급자 비밀 정보를 반환하지 않는다. 로그인 갱신 실패나 주문 재시도 같은 프론트 행동도 오류 코드별로 합의한다.

## 4. 인증과 권한

- 백엔드 로그인 인증은 Spring Security + JWT로 확정한다. 액세스 토큰은 JWT이며 공개 API에 Authorization: Bearer로 전달한다. 리프레시는 기존 명세에 따라 HttpOnly 쿠키로 전달하고 서버에서 유효성·폐기를 관리한다. 리프레시 토큰 자체의 JWT/불투명 형식은 별도 결정한다.
- JWT 서명·만료·issuer·audience를 검증하고 허용 알고리즘을 고정한다. 서명키는 Secret으로 관리하며 토큰·비밀번호를 로그에 남기지 않는다. 액세스 1시간·리프레시 14일은 기존 명세의 제안값이며 구현 전에 승인한다.
- 쿠키 갱신·로그아웃은 CSRF 토큰과 Origin을 검사한다. 도메인·CORS·쿠키 정책은 배포 환경과 함께 확정한다.
- 초기 운영은 하나의 공개 도메인에서 웹과 /api를 제공하는 구조를 추천한다. 프론트가 별도 배포되어도 리버스 프록시로 같은 사이트를 제공할 수 있다. 도메인을 분리한다면 쿠키 설계를 재검토한다.
- 본인 계좌·주문 권한은 백엔드가 검사한다. 로그인 여부만으로 소유권을 인정하지 않는다.
- 내부 AI API는 백엔드용 서비스 인증과 네트워크 접근 제한을 적용한다. 사용자 액세스 토큰을 무조건 전달하지 않는다.
- Secret 값은 레포별 배포 환경에 저장한다. 서버 간 공유 인증 값은 두 배포 환경에서 일치시켜야 하지만 Git 문서에는 실제 값을 적지 않는다.

## 5. 내부 AI 계약에서 반드시 정할 필드

아래는 계약 설계 항목이며 실제 API 구현이나 기존 명세에 추가된 확정 필드가 아니다.

| 요청 항목 | 합의 내용 |
| --- | --- |
| 요청 ID | 백엔드가 발급하고 AI·로그로 전달 |
| 질문 | 길이·허용 형식·빈 입력 처리 |
| 기업·기간 문맥 | 식별자·회계기간 기준. 사용자 입력과 서버 검증 결과 구분 |
| 대화 문맥 | 이전 대화를 지원할지와 길이·보존·권한 기준 |
| 개인화 문맥 | 1차 개인 계좌 도구는 후속 범위. 추가 시 본인 권한 확인 후 최소 데이터만 전달 |

| 응답 항목 | 합의 내용 |
| --- | --- |
| 답변 | 핵심 설명과 정형 수치·단위·기간 |
| 결과 상태 | 정상·추가 질문 필요·근거 부족을 구분. 도구 장애는 오류로 구분 |
| 출처 | 공시·재무 식별자, 제목, 공시일, 버전, 청크 또는 재무 항목 근거 |
| 계산 | 지표, 공식, 입력 값, 기간·회계 기준 |
| 오류 | 코드, 재시도 가능 여부. 공개 API 매핑은 백엔드 책임 |

근거 부족은 시스템 장애와 다르다. 근거 부족을 성공한 분석처럼 표현하거나 도구 장애를 근거 부족으로 숨기지 않는다. 출처 식별자는 이후 원문을 확인할 수 있도록 안정적으로 유지한다.

## 6. 데이터 소유권과 식별자

백엔드는 사용자·계좌·거래·종목·랭킹·관심목록과 사용자 AI 답변 이력을 소유한다. AI는 기업·공시·재무·청크·임베딩·수집 작업을 소유한다. 상대 서비스 DB를 직접 변경하지 않는다.

companyId는 AI 데이터 영역에서 발급하고, 백엔드의 종목 매핑은 AI의 기업 식별 정보를 검증한 뒤 저장하는 안을 제안한다. instrumentId는 백엔드가 발급한다. 공시 정정은 문서 버전으로 구분하며 기존 답변의 근거를 새 버전으로 조용히 바꾸지 않는다.

종목·기업 연결과 답변 출처의 서비스 간 ID는 서비스 독립성을 위해 DB 간 FK를 사용하지 않고 계약과 동기화 검증으로 관리한다. MySQL의 두 DB에 각각 전용 계정·마이그레이션 책임을 둔다. 기존 ERD를 수정해 ID 발급 책임, 누락 처리, 삭제·보존 규칙을 명시한 후 구현한다.

## 7. 호출 제한시간·재시도·추적

- 백엔드의 X-Request-Id를 AI에 전달하고 양쪽 로그에서 같은 ID로 조회한다. 브라우저 요청 ID 입력은 검증하거나 서버에서 교체한다.
- AI 최대 처리시간, 백엔드 내부 호출 제한시간, 공개 진입점 제한시간, 프론트 대기시간을 일관되게 정한다. AI 처리시간 < 백엔드 제한시간 < 진입점·클라이언트 대기시간 순서를 기준으로 여유 시간을 둔다.
- AI 동시 요청 수·질문 길이·LLM 토큰·사용자 호출 한도를 정한다. 정확한 값은 표본 질의의 지연·비용 측정 후 확정한다.
- LLM 비용과 답변 이력 중복을 방지하기 전에는 AI 분석 POST를 자동 재시도하지 않는다. 제한시간 초과가 작업 중단을 보장하지 않음을 고려한다.
- 계좌 생성·주문·초기화는 기존 Idempotency-Key 규칙을 유지한다. 같은 키의 재사용·충돌·진행 중 상태를 모든 소비자가 동일하게 처리한다.
- 질문 전문·개인 정보·토큰은 무조건 로그에 남기지 않는다. 필요한 추적 정보와 답변 보존 정책을 구분한다.

## 8. 레포 간 변경 절차

1. 이슈에 영향받는 레포·API·데이터·배포 순서를 기록한다.
2. API 제공자 레포에서 계약과 예시를 먼저 검토한다. 관련 소비자 담당자가 참여한다.
3. 제공자와 소비자 PR을 상호 링크한다. 소비자는 합의한 계약 태그·커밋을 고정한다.
4. 제공자 응답이 계약에 맞는지 검사하고 소비자가 처리하는 정상·빈값·근거 부족·오류 사례를 확인한다.
5. 선택한 세 앱 버전으로 스테이징 통합 검증을 수행한다.
6. 호환성을 유지하는 순서로 배포하고 실제 배포 버전 조합을 기록한다.

필드 삭제, 필수 요청값 추가, 타입·단위·상태 의미 변경은 호환성 파괴로 취급한다. 선택 응답 필드 추가도 소비자가 미지 필드를 허용하는지 검증한다. 앱 버전과 API 버전은 별개이며, 단순 앱 배포마다 /v2를 만들지 않는다.

예: AI 답변에 새 선택 출처 필드를 추가한다면 AI가 기존 백엔드와 호환되는 응답을 먼저 제공 → 백엔드가 이를 공개 응답에 연결 → 프론트가 출처 UI를 사용한다. 필드를 교체할 때는 일정 기간 신·구 필드를 함께 지원하고 소비자 전환을 확인한 뒤 구형 필드를 제거한다.

## 9. CI·통합 실행·릴리스

각 레포 CI는 해당 언어의 빌드·검사와 제공 계약 또는 소비 계약의 검증을 수행한다. 모든 PR에서 세 레포 최신 브랜치를 무조건 조합하지 않는다. 계약 변경 PR은 관련 소비자와 검증할 커밋을 지정한다.

전체 통합 실행은 백엔드의 infra/compose.integration.yaml을 기준으로 한다. 기본 실행은 버전이 고정된 이미지를 사용하고, 로컬 개발 앱만 소스 실행으로 대체할 수 있게 한다. DB·Redis·AI·백엔드의 준비 상태와 마이그레이션 순서를 정의한다.

backend/docs/releases에는 다음 버전 조합을 기록한다.

```yaml
# 형식 예시이며 실행 가능한 배포 파일이 아님
webCommit: <검증한 커밋>
backendCommit: <검증한 커밋>
aiCommit: <검증한 커밋>
publicContractCommit: <백엔드 계약 커밋>
internalAiContractCommit: <AI 계약 커밋>
backendImage: <불변 태그 또는 digest>
aiImage: <불변 태그 또는 digest>
webArtifact: <프론트 배포 식별자>
```

실제 배포는 latest에 의존하지 않는다. 앱별 릴리스 번호는 같을 필요가 없다. DB 변경은 확장 → 앱 전환 → 구형 구조 제거 순서로 호환성을 유지하고, 되돌릴 수 있는 앱 버전과 DB 변경의 관계를 확인한다.

공통 핵심 검증: 로그인·갱신, 주문 접수·체결·초기화, 재무 질의·계산·공시 출처, 근거 부족, AI 장애 시 거래 기능 정상 동작. 단위 검사만으로 레포 간 호환성을 확인한 것으로 간주하지 않는다.

## 10. Git 컨벤션과 PR 규칙

### 10.1 브랜치

main은 검증된 기본 브랜치로 사용하고 직접 push하지 않는다. 별도 develop 브랜치는 초기 필수로 두지 않는다. main에서 작업 브랜치를 만들고 PR로 변경한다.

형식: `<type>/<레포 내 이슈번호>-<영문-kebab-case>`

```text
feat/12-jwt-login
fix/18-order-reservation
refactor/23-account-validation
docs/7-system-architecture
chore/9-ci-setup
hotfix/31-token-validation
```

feat, fix, refactor, docs, test, chore, ci, perf, hotfix를 사용한다. 이슈 번호는 레포별이므로 상대 레포 이슈는 `조직/레포#번호` 또는 URL로 참조한다. 짧은 기능 브랜치를 사용하며 완료된 브랜치는 머지 후 삭제한다.

### 10.2 커밋 메시지

형식: `<type>(<scope>): <한국어 또는 영어 변경 요약>`

scope는 선택이며 auth, trading, market, research, rag, ingestion, infra, docs 등 실제 변경 영역을 적는다. 이 목록은 담당자 배정이 아니다.

| type | 용도 |
| --- | --- |
| feat | 사용자·서비스 기능 추가 |
| fix | 오류 수정 |
| refactor | 동작 의미를 유지하는 구조 개선 |
| docs | 문서·명세 수정 |
| test | 테스트 추가·수정 |
| chore | 의존성·도구·관리 작업 |
| ci | CI·배포 파이프라인 변경 |
| perf | 성능 개선 |
| style | 동작 변화 없는 포맷 수정 |
| revert | 기존 변경 되돌림 |

```text
feat(auth): JWT 로그인 API 추가
fix(trading): 동시 주문의 예약금 초과 방지
docs(architecture): MySQL 데이터 소유권 명시
ci(backend): Gradle 빌드 검사 추가
```

관련 변경만 한 커밋에 담고 `수정`, `작업 중`, `최종` 같은 모호한 요약을 사용하지 않는다. 본문이 필요하면 변경 이유와 영향·검증을 기록한다. 각 커밋 본문에는 `Refs #12` 형식으로 해당 레포 이슈를 연결하고 PR 본문에도 연결한다. 상대 레포 이슈는 전체 레포 이름 또는 URL을 사용한다. 의도적인 호환성 파괴는 `feat(api)!: ...`와 `BREAKING CHANGE:` 설명으로 표시하되, 배포 전환 계획을 반드시 포함한다.

### 10.3 이슈와 PR

**모든 변경은 작업 전에 해당 레포에 이슈를 등록한다. 기능·버그·문서·명세·인프라·CI·긴급 수정에도 예외 없이 적용한다.** 이슈에 목적·완료 기준·담당자·관련 레포와 유형 라벨을 기록한다. 브랜치 이름에 이슈 번호를 넣고, 각 커밋 본문에 `Refs #12`처럼 연결하며, PR 본문에도 관련 이슈를 연결한다. 같은 목적의 기존 이슈가 있다면 재사용하고 PR에 설명한다. 기능별 백엔드 분담은 송상진·박진호가 이슈에서 합의한다. PR은 한 목적 중심으로 만들고 미완료는 Draft로 표시한다.

PR 제목은 커밋 형식과 동일하게 작성한다. PR 본문에 다음을 기록한다.

```markdown
## 변경 목적과 결과

## 관련 이슈·레포 PR

## API·DB·인증 변경

## 검증 결과

## 배포 순서·호환성·롤백 영향
```

영향 없는 항목은 해당 없음으로 표시한다. 예: 이슈 `#12` 등록 → `feat/12-jwt-login` 브랜치 생성 → `feat(auth): JWT 로그인 API 추가` 커밋(본문 `Refs #12`) → PR 본문에 `Closes #12` → 회의에서 설명 후 작성자 머지. `feat` 등 유형 라벨은 이슈 분류용이고 `v1.0.0` 같은 Git 릴리스 태그와 다르다.

이슈 종료 키워드 `Closes #12`는 해당 레포의 이슈를 실제 완료하는 경우에만 사용한다. 상대 레포 작업이 남아 있으면 연결하고 완료 상태를 구분한다.

### 10.4 리뷰·머지 — 모든 PR에 적용

작성자는 회의에서 PR 변경 내용·검증 결과·영향을 설명하고 논의 사항을 반영한 뒤 자신의 PR을 직접 머지할 수 있다. GitHub 승인 리뷰는 필수가 아니다.

- 모든 변경은 이슈·브랜치·PR로 연결하고 필수 CI를 통과해야 한다.
- API·DB·인증·인프라 변경은 영향받는 담당자와 확인한다.
- 미해결 대화를 해결한 뒤 Squash and merge한다. 최종 메시지는 PR 제목 컨벤션을 따른다.
- main 직접 push·force push·삭제는 금지한다. 오류는 fix/revert PR로 수정한다.

### 10.5 GitHub 보호 설정

main의 PR 필수·필수 CI·최신 main 기준 검사·대화 해결·force push 및 삭제 금지는 유지한다. 필수 승인 인원과 자기 PR 머지 제한은 적용하지 않는다. CODEOWNERS는 계정 확인 후 담당 안내 용도로 검토하며 필수 승인 조건으로 사용하지 않는다.

근거: [GitHub 필수 리뷰](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews), [Ruleset 규칙](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

### 10.6 릴리스와 제외 파일

레포별 릴리스 태그는 `v<major>.<minor>.<patch>`를 사용한다. 앱 태그와 API 경로 버전은 구분하며 세 레포 태그 번호를 맞출 필요는 없다. 배포 조합은 9절 기준으로 기록한다.

실제 `.env`, 키·토큰·인증서 개인키, `.venv`, `node_modules`, 빌드 결과, 개인 IDE 설정은 커밋하지 않는다. Gradle Wrapper, uv.lock 및 추후 선택할 프론트 lockfile은 커밋한다. 이미 적용된 DB 마이그레이션 파일을 임의 수정하지 않고 신규 마이그레이션으로 변경한다.

완료 조건은 해당 레포 코드 머지뿐 아니라 필요한 상대 레포 전환과 통합 검증까지 포함한다.

참조: [시스템 아키텍처](system-architecture.md). 이 문서는 규약이며 GitHub 보호 설정·CODEOWNERS·CI·머지 App을 실제 생성하거나 적용한 결과는 아니다.

## 11. 현재 기술 결정 반영

backend는 Java 21 LTS(Eclipse Temurin) + Spring Boot 4.1.1 + Gradle을 사용한다. Java 주 버전과 Spring Boot 버전은 확정이며 개발·CI·컨테이너에 동일하게 적용한다. Gradle Wrapper는 공식 Initializr가 제공한 9.7.1로 고정한다. JDK 패치 버전은 보안 업데이트에 따라 관리한다. RDB는 MySQL을 사용하고 8.4 LTS를 추천한다. AI는 Python 3.12 + FastAPI + uv를 추천하며 상세 라이브러리는 시스템 아키텍처 1.3절을 따른다.

프론트 기술·배포는 미정이며 백엔드 먼저 구현한다. web의 TypeScript 클라이언트·Node CI·독립 배포는 아직 확정하지 않는다. 별도 프론트 선택 시 기존 3레포 규약을 적용한다. Thymeleaf 선택 시 화면을 백엔드 templates/static에 포함하고 web 레포와 3앱 릴리스 조합은 재검토한다. 백엔드 로그인 JWT 선택은 유지한다. Thymeleaf 선택 시 브라우저의 JWT 전달·보관 방식과 서버 렌더링·CSRF 처리를 별도로 설계한다. 백엔드 API와 AI의 내부 계약은 화면 방식과 관계없이 유지한다.
