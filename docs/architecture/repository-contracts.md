# InvestLab 레포 간 협업 규약

작성일: 2026-10-10 (KST)
최종 수정: 2026-10-25 (KST)

상태: investlab-team의 3개 레포에 적용하는 협업 규약. 이슈·PR 양식과 CI는 현재 파일을 기준으로 정리했다. 제한시간·운영 배포 환경 등 미확정 설계는 별도로 합의한다. 기존 공개 API 정책은 유지하며 내부 AI 계약의 상세 구현은 후속 작업이다.

## 1. 책임과 기준 위치

### 1.1 팀 담당

프론트 담당과 기술은 미정이다. 확정된 A/B/C 기능 담당은 [API 명세 및 담당 표](../api/README.md)를 따른다. 권장·후속 기능과 담당 변경은 이슈에서 합의하고 표를 함께 갱신한다. 담당자는 구현·기준 유지 책임자이며 회의 설명과 CI 통과 후 자기 PR을 머지할 수 있다.

조직 `investlab-team` 생성과 팀원 3명의 가입은 완료했다. 현재 조직 멤버 계정은 `@song-sang-jin`, `@koreanguyyyy`, `@nmj05172`다. 조직 가입과 레포 쓰기·머지 권한은 별개이므로 실제 작업 권한은 레포별 접근 설정을 따른다. CODEOWNERS는 필요한 경우 담당 안내용으로 도입하며, 필수 승인 조건으로 사용하지 않는다.

여기서 계약은 URL, 요청·응답 필드, 타입, 필수 여부, 상태·오류, 인증, 동작 의미까지 포함한 약속이다. Java 엔티티·Python 모델·향후 프론트 타입을 동일한 소스 파일로 공유할 필요는 없다.

소비자는 제공자 레포의 특정 태그나 커밋에서 계약을 가져온다. 브랜치 최신 파일을 매번 가져오지 않는다. 별도 패키지 레지스트리 없이 시작할 수 있으며, 비공개 레포의 CI 접근은 최소 읽기 권한으로 설정한다. 생성 클라이언트·타입을 커밋한다면 생성 명령과 기준 계약 커밋을 함께 기록한다.

## 3. 공개 응답과 오류

기존 API 명세의 형식을 유지한다.

```json
{
  "data": {},
  "meta": { "requestId": "요청 식별자" }
}
```

```json
{
  "error": {
    "code": "DATA_UNAVAILABLE",
    "message": "데이터를 조회할 수 없습니다.",
    "details": []
  },
  "requestId": "요청 식별자"
}
```

빈 목록, 리소스 없음, 권한 거부, 가격 지연, 외부 장애를 구분한다. 기존 400/401/403/404/409/422/429/503 의미를 유지한다. 내부 AI 실패는 백엔드에서 공개 오류로 변환하며 내부 URL·스택·공급자 비밀 정보를 반환하지 않는다. 로그인 갱신 실패나 주문 재시도 같은 프론트 행동도 오류 코드별로 합의한다.

## 4. 인증과 권한

- 백엔드 로그인 인증은 Spring Security + JWT로 확정한다. 액세스 토큰은 JWT이며 공개 API에 Authorization: Bearer로 전달한다. 리프레시는 기존 명세에 따라 HttpOnly 쿠키로 전달하고 서버에서 유효성·폐기를 관리한다. 리프레시 토큰 자체의 JWT/불투명 형식은 별도 결정한다.
- JWT 서명·만료·issuer·audience를 검증하고 허용 알고리즘을 고정한다. 서명키는 Secret으로 관리하며 토큰·비밀번호를 로그에 남기지 않는다. 액세스 1시간·리프레시 14일은 기존 명세의 제안값이며 구현 전에 승인한다.
- 쿠키 갱신·로그아웃은 CSRF 토큰과 Origin을 검사한다. 도메인·CORS·쿠키 정책은 배포 환경과 함께 확정한다.
- 초기 운영은 하나의 공개 도메인에서 웹과 /api를 제공하는 구조를 추천한다. 프론트가 별도 배포되어도 리버스 프록시로 같은 사이트를 제공할 수 있다. 도메인을 분리한다면 쿠키 설계를 재검토한다.
- 본인 계좌·주문 권한은 백엔드가 검사한다. 로그인 여부만으로 소유권을 인정하지 않는다.
- 내부 AI API는 백엔드용 서비스 인증과 네트워크 접근 제한을 적용한다. 사용자 액세스 토큰을 무조건 전달하지 않는다.
- Secret 값은 레포별 배포 환경에 저장한다. 서버 간 공유 인증 값은 두 배포 환경에서 일치시켜야 하지만 Git 문서에는 실제 값을 적지 않는다.

## 5. 내부 AI 계약에서 반드시 정할 필드

아래는 계약 설계 항목이며 실제 API 구현이나 기존 명세에 추가된 확정 필드가 아니다.

| 요청 항목       | 합의 내용                                                                    |
| --------------- | ---------------------------------------------------------------------------- |
| 요청 ID         | 백엔드가 발급하고 AI·로그로 전달                                            |
| 질문            | 길이·허용 형식·빈 입력 처리                                                |
| 기업·기간 문맥 | 식별자·회계기간 기준. 사용자 입력과 서버 검증 결과 구분                     |
| 대화 문맥       | 이전 대화를 지원할지와 길이·보존·권한 기준                                 |
| 개인화 문맥     | 1차 개인 계좌 도구는 후속 범위. 추가 시 본인 권한 확인 후 최소 데이터만 전달 |

| 응답 항목 | 합의 내용                                                       |
| --------- | --------------------------------------------------------------- |
| 답변      | 핵심 설명과 정형 수치·단위·기간                               |
| 결과 상태 | 정상·추가 질문 필요·근거 부족을 구분. 도구 장애는 오류로 구분 |
| 출처      | 공시·재무 식별자, 제목, 공시일, 버전, 청크 또는 재무 항목 근거 |
| 계산      | 지표, 공식, 입력 값, 기간·회계 기준                            |
| 오류      | 코드, 재시도 가능 여부. 공개 API 매핑은 백엔드 책임             |

근거 부족은 시스템 장애와 다르다. 근거 부족을 성공한 분석처럼 표현하거나 도구 장애를 근거 부족으로 숨기지 않는다. 출처 식별자는 이후 원문을 확인할 수 있도록 안정적으로 유지한다.

## 6. 데이터 소유권과 식별자

백엔드는 사용자·계좌·거래·종목·랭킹·관심목록과 사용자 AI 답변 이력을 소유한다. AI는 기업·공시·재무·청크·임베딩·수집 작업을 소유한다. 상대 서비스 DB를 직접 변경하지 않는다.

companyId는 AI 데이터 영역에서 발급하고, 백엔드의 종목 매핑은 AI의 기업 식별 정보를 검증한 뒤 저장하는 안을 제안한다. instrumentId는 백엔드가 발급한다. 공시 정정은 문서 버전으로 구분하며 기존 답변의 근거를 새 버전으로 조용히 바꾸지 않는다.

종목·기업 연결과 답변 출처의 서비스 간 ID는 서비스 독립성을 위해 DB 간 FK를 사용하지 않고 계약과 동기화 검증으로 관리한다. PostgreSQL의 두 DB에 각각 전용 계정·마이그레이션 책임을 둔다. 기존 ERD를 수정해 ID 발급 책임, 누락 처리, 삭제·보존 규칙을 명시한 후 구현한다.

## 7. 호출 제한시간·재시도·추적

- 백엔드의 X-Request-Id를 AI에 전달하고 양쪽 로그에서 같은 ID로 조회한다. 브라우저 요청 ID 입력은 검증하거나 서버에서 교체한다.
- AI 최대 처리시간, 백엔드 내부 호출 제한시간, 공개 진입점 제한시간, 프론트 대기시간을 일관되게 정한다. AI 처리시간 < 백엔드 제한시간 < 진입점·클라이언트 대기시간 순서를 기준으로 여유 시간을 둔다.
- AI 동시 요청 수·질문 길이·LLM 토큰·사용자 호출 한도를 정한다. 정확한 값은 표본 질의의 지연·비용 측정 후 확정한다.
- LLM 비용과 답변 이력 중복을 방지하기 전에는 AI 분석 POST를 자동 재시도하지 않는다. 제한시간 초과가 작업 중단을 보장하지 않음을 고려한다.
- 계좌 생성·주문·초기화는 기존 Idempotency-Key 규칙을 유지한다. 같은 키의 재사용·충돌·진행 중 상태를 모든 소비자가 동일하게 처리한다.
- 질문 전문·개인 정보·토큰은 무조건 로그에 남기지 않는다. 필요한 추적 정보와 답변 보존 정책을 구분한다.

## 8. 레포 간 변경 절차

1. 이슈에 영향받는 레포·API·데이터·배포 순서를 기록한다.
2. API 제공자 레포에서 계약과 예시를 먼저 검토한다. 관련 소비자 담당자가 참여한다.
3. 제공자와 소비자 PR을 상호 링크한다. 소비자는 합의한 계약 태그·커밋을 고정한다.
4. 제공자 응답이 계약에 맞는지 검사하고 소비자가 처리하는 정상·빈값·근거 부족·오류 사례를 확인한다.
5. 선택한 세 앱 버전으로 스테이징 통합 검증을 수행한다.
6. 호환성을 유지하는 순서로 배포하고 실제 배포 버전 조합을 기록한다.

필드 삭제, 필수 요청값 추가, 타입·단위·상태 의미 변경은 호환성 파괴로 취급한다. 선택 응답 필드 추가도 소비자가 미지 필드를 허용하는지 검증한다. 앱 버전과 API 버전은 별개이며, 단순 앱 배포마다 /v2를 만들지 않는다.

예: AI 답변에 새 선택 출처 필드를 추가한다면 AI가 기존 백엔드와 호환되는 응답을 먼저 제공 → 백엔드가 이를 공개 응답에 연결 → 프론트가 출처 UI를 사용한다. 필드를 교체할 때는 일정 기간 신·구 필드를 함께 지원하고 소비자 전환을 확인한 뒤 구형 필드를 제거한다.

## 9. CI·통합 실행·릴리스

현재 자동 CI는 PR 작성 규칙과 백엔드·AI의 빌드·코드 검사·테스트다. 제공·소비 API 계약 및 레포 간 통합 검증은 모두 자동화된 상태가 아니므로, 관련 변경 PR에서 필요한 검증과 대상 커밋을 별도로 기록한다. 모든 PR에서 세 레포 최신 브랜치를 무조건 조합하지 않는다. 실제 실행 명령은 12.7절을 따른다.

전체 통합 실행 설정은 백엔드의 `infra/compose.integration.yaml`을 기준으로 한다. 현재 PostgreSQL 16과 선택 실행하는 백엔드·AI 구성이며 Redis는 포함하지 않는다. 로컬에서 앱을 직접 실행할 수도 있다. 운영용 불변 이미지 버전·배포 순서는 별도로 확정한다.

운영 배포를 구성할 때 `investlab-backend/docs/releases`에 다음 버전 조합을 기록한다. 아래는 향후 기록 형식이며 현재 생성된 배포 기록을 의미하지 않는다.

```yaml
# 형식 예시이며 실행 가능한 배포 파일이 아님
webCommit: <검증한 커밋>
backendCommit: <검증한 커밋>
aiCommit: <검증한 커밋>
publicContractCommit: <백엔드 계약 커밋>
internalAiContractCommit: <AI 계약 커밋>
backendImage: <불변 태그 또는 digest>
aiImage: <불변 태그 또는 digest>
webArtifact: <프론트 배포 식별자>
```

실제 배포는 latest에 의존하지 않는다. 앱별 릴리스 번호는 같을 필요가 없다. DB 변경은 확장 → 앱 전환 → 구형 구조 제거 순서로 호환성을 유지하고, 되돌릴 수 있는 앱 버전과 DB 변경의 관계를 확인한다.

공통 핵심 검증: 로그인·갱신, 주문 접수·체결·초기화, 재무 질의·계산·공시 출처, 근거 부족, AI 장애 시 거래 기능 정상 동작. 단위 검사만으로 레포 간 호환성을 확인한 것으로 간주하지 않는다.

## 10. Git 컨벤션과 PR 규칙

### 10.1 브랜치

세 레포의 기본·개발 통합 브랜치는 `dev`다. 최신 `dev`에서 이슈별 작업 브랜치를 만들고 PR의 base는 `dev`로 설정한다. `dev`와 `main`에 직접 push하지 않는다. `main`은 릴리스 기준으로 보존하며 팀이 릴리스 범위·시점을 합의한 뒤 별도 PR로 반영한다. 일상 기능 PR은 `main`으로 보내지 않는다.

형식: `<type>/<레포 내 이슈번호>-<영문-kebab-case>`

```text
feat/12-jwt-login
fix/18-order-reservation
refactor/23-account-validation
docs/7-system-architecture
chore/9-ci-setup
hotfix/31-token-validation
```

feat, fix, refactor, docs, test, chore, ci, perf, hotfix를 사용한다. 이슈 번호는 레포별이므로 상대 레포 이슈는 `조직/레포#번호` 또는 URL로 참조한다. 짧은 기능 브랜치를 사용하며 완료된 브랜치는 머지 후 삭제한다.

### 10.2 커밋 메시지

형식: `<type>(<scope>): <한국어 또는 영어 변경 요약>`

scope는 선택이며 auth, trading, market, research, rag, ingestion, infra, docs 등 실제 변경 영역을 적는다. 이 목록은 담당자 배정이 아니다.

| type     | 용도                           |
| -------- | ------------------------------ |
| feat     | 사용자·서비스 기능 추가       |
| fix      | 오류 수정                      |
| refactor | 동작 의미를 유지하는 구조 개선 |
| docs     | 문서·명세 수정                |
| test     | 테스트 추가·수정              |
| chore    | 의존성·도구·관리 작업        |
| ci       | CI·배포 파이프라인 변경       |
| perf     | 성능 개선                      |
| style    | 동작 변화 없는 포맷 수정       |
| revert   | 기존 변경 되돌림               |

```text
feat(auth): JWT 로그인 API 추가
fix(trading): 동시 주문의 예약금 초과 방지
docs(architecture): PostgreSQL 데이터 소유권 명시
ci(backend): Gradle 빌드 검사 추가
```

관련 변경만 한 커밋에 담고 `수정`, `작업 중`, `최종` 같은 모호한 요약을 사용하지 않는다. 본문이 필요하면 변경 이유와 영향·검증을 기록한다. 각 커밋 본문에는 `Refs #12` 형식으로 해당 레포 이슈를 연결하고 PR 본문에도 연결한다. 상대 레포 이슈는 전체 레포 이름 또는 URL을 사용한다. 의도적인 호환성 파괴는 `feat(api)!: ...`와 `BREAKING CHANGE:` 설명으로 표시하되, 배포 전환 계획을 반드시 포함한다.

### 10.3 이슈와 PR

**모든 변경은 작업 전에 해당 레포에 이슈를 등록한다. 기능·버그·문서·명세·인프라·CI·긴급 수정에도 예외 없이 적용한다.** 이슈에는 담당자·작업 내용·완료 기준을 필수로 적고 추가 사항은 필요할 때만 작성한다. 버그 폼은 작업 내용 대신 문제와 재현 방법을 작성한다. 담당자는 폼의 담당자 입력란에 이름 / @아이디로 기록하고 일정은 Project에서 관리한다. 목적은 작업 내용에 필요할 때 한 문장으로 적는다. 브랜치 이름에 이슈 번호를 넣고, 각 커밋 본문에 `Refs #12`처럼 연결하며, PR 본문에도 관련 이슈를 연결한다. 같은 목적의 기존 이슈가 있다면 재사용하고 PR에 설명한다. 기능별 담당은 API 담당 표를 기준으로 이슈에 기록하며, 분담 변경은 송상진·박진호가 합의해 문서에도 반영한다. PR은 한 목적 중심으로 만들고 미완료는 Draft로 표시한다.

PR 제목은 커밋 형식과 동일하게 작성한다. PR 본문에 다음을 기록한다.

```markdown
## 변경 내용
- 실제로 구현·수정한 내용

## 관련 이슈
Closes #완료한이슈번호
Refs #참조이슈번호 (필요할 때 추가)

## 검증 결과
- 실제 실행한 검증과 결과 (미실행이면 이유)

## 추가 사항 (선택)
없음
```

추가 사항은 영향이 없으면 없음으로 둔다. API·DB·인증·환경 변수·배포 순서 등의 변경이 있으면 추가 사항에 필요한 내용만 기록한다. PR 템플릿의 주석에는 완료 이슈 Closes #42, 참조·일부 작업 이슈 Refs #35 예시를 제공한다. 예시 번호를 실제 번호로 바꾸고 필요한 만큼 함께 작성할 수 있다. PR은 한 목적에 집중하되 이슈를 여러 개 연결할 수 있으며, 같은 이슈에 두 키워드를 중복할 필요는 없다. 브랜치의 이슈 번호도 본문에 포함한다. 예: 이슈 `#12` 등록 → `feat/12-jwt-login` 브랜치 생성 → `feat(auth): JWT 로그인 API 추가` 커밋(본문 `Refs #12`) → PR 본문에 `Closes #12` → 회의에서 설명 후 작성자 머지. `feat` 등 유형 라벨은 이슈 분류용이고 `v1.0.0` 같은 Git 릴리스 태그와 다르다.

이슈 종료 키워드 `Closes #12`는 해당 레포의 이슈를 실제 완료하는 경우에만 사용한다. 상대 레포 작업이 남아 있으면 연결하고 완료 상태를 구분한다.

PR의 **검증 결과**는 이번 변경을 확인한 방법과 실제 결과다. 테스트 코드 작성·실행뿐 아니라 API 직접 호출, 서버 시작·상태 응답, 문서 미리보기 확인 등 작업에 맞는 검증을 적는다. 미실행이면 이유와 확인하지 못한 범위를 적고, 필요한 검증을 완료한 후 머지한다. `git diff --check`는 공백 등 형식 확인일 뿐 기능 검증을 대체하지 않는다.

**추가 사항**에는 관련 API·DB 마이그레이션·환경 변수 이름·배포 순서·다른 레포 PR 등 필요한 정보만 적는다. 비밀값은 적지 않는다. PR 템플릿의 HTML 주석에 각 항목의 작성 예시를 제공하며, 주석 아래에 실제 내용을 작성한다. 추가 사항이 없으면 `없음`을 유지한다.

### 10.4 리뷰·머지 — 모든 PR에 적용

작성자는 회의에서 PR 변경 내용·검증 결과·영향을 설명하고 논의 사항을 반영한 뒤 자신의 PR을 직접 머지할 수 있다. GitHub 승인 리뷰는 필수가 아니다.

- 모든 변경은 이슈·브랜치·PR로 연결하고 필수 CI를 통과해야 한다.
- API·DB·인증·인프라 변경은 영향받는 담당자와 확인한다.
- 미해결 대화를 해결한 뒤 Squash and merge한다. 최종 메시지는 PR 제목 컨벤션을 따른다.
- dev·main 직접 push·force push·삭제는 금지한다. 오류는 fix/revert PR로 수정한다.

### 10.5 GitHub 보호 설정

dev와 main의 PR 필수·필수 CI·각 대상 브랜치 최신 기준 검사·대화 해결·force push 및 삭제 금지는 유지한다. 필수 승인 인원과 자기 PR 머지 제한은 적용하지 않는다. CODEOWNERS는 필요한 경우 담당 안내 용도로 검토하며 필수 승인 조건으로 사용하지 않는다.

근거: [GitHub 필수 리뷰](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews), [Ruleset 규칙](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

### 10.6 릴리스와 제외 파일

레포별 릴리스 태그는 `v<major>.<minor>.<patch>`를 사용한다. 앱 태그와 API 경로 버전은 구분하며 세 레포 태그 번호를 맞출 필요는 없다. 배포 조합은 9절 기준으로 기록한다.

실제 `.env`, 키·토큰·인증서 개인키, `.venv`, `node_modules`, 빌드 결과, 개인 IDE 설정은 커밋하지 않는다. Gradle Wrapper, uv.lock 및 추후 선택할 프론트 lockfile은 커밋한다. 이미 적용된 DB 마이그레이션 파일을 임의 수정하지 않고 신규 마이그레이션으로 변경한다.

완료 조건은 해당 레포 코드 머지뿐 아니라 필요한 상대 레포 전환과 통합 검증까지 포함한다.

참조: [시스템 아키텍처](system-architecture.md). CI의 기준은 각 레포 `.github/workflows`, 이슈·PR 양식의 기준은 `.github/ISSUE_TEMPLATE` 및 `.github/pull_request_template.md`다. 브랜치 보호·접근 권한은 GitHub Settings에서 관리하며 이 문서를 수정한다고 설정이 자동 변경되는 것은 아니다.

## 11. 현재 기술 결정 반영

backend는 Java 21 LTS(Eclipse Temurin) + Spring Boot 4.1.1 + Gradle을 사용한다. Java 주 버전과 Spring Boot 버전은 확정이며 개발·CI·컨테이너에 동일하게 적용한다. Gradle Wrapper는 공식 Initializr가 제공한 9.7.1로 고정한다. JDK 패치 버전은 보안 업데이트에 따라 관리한다. RDB는 PostgreSQL 16을 사용한다. AI는 Python 3.12 + FastAPI + uv를 추천하며 상세 라이브러리는 시스템 아키텍처 1.3절을 따른다.

프론트 기술·배포는 미정이며 백엔드 먼저 구현한다. web의 TypeScript 클라이언트·Node CI·독립 배포는 아직 확정하지 않는다. 별도 프론트 선택 시 기존 3레포 규약을 적용한다. Thymeleaf 선택 시 화면을 백엔드 templates/static에 포함하고 web 레포와 3앱 릴리스 조합은 재검토한다. 백엔드 로그인 JWT 선택은 유지한다. Thymeleaf 선택 시 브라우저의 JWT 전달·보관 방식과 서버 렌더링·CSRF 처리를 별도로 설계한다. 백엔드 API와 AI의 내부 계약은 화면 방식과 관계없이 유지한다.

## 12. 이슈·PR 작성과 현재 CI

세 레포 공통 안내다. 번호와 기능은 설명용 예시이며 실제 이슈 번호와 작업으로 바꿔 작성한다. 아래 기능이나 버그가 구현·확인되었다는 의미는 아니다.

### 12.1 이슈 작성 기준

| 항목 | 기능·설정·문서 작업 | 버그 수정 |
| --- | --- | --- |
| 담당자 (필수) | 이름 / @GitHub아이디 | 동일 |
| 작업 설명 (필수) | 작업 내용 | 문제와 재현 방법 |
| 완료 기준 (필수) | 확인할 결과를 체크리스트로 작성 | 수정 결과와 기존 정상 동작 확인 조건 |
| 추가 사항 (선택) | 기본값 없음. 관련 API·이슈·다른 레포 영향·DB·환경 변수·배포 주의점이 있을 때만 작성 | 동일 |

담당자는 폼에서 직접 입력한다. 이름 입력이나 @멘션은 GitHub Assignees를 자동 지정하지 않는다. Project의 Assignees 열에 표시할 필요가 있으면 별도로 지정한다. 일정은 Project에서 관리한다.

작업 내용은 할 일이고, 완료 기준은 결과를 확인할 조건이다. 등록 시 체크하지 않고, 구현·검증 후 담당자가 직접 체크한다. 검증은 테스트 코드나 API 직접 호출 등 작업에 맞는 방식으로 수행한다. CI 결과는 PR에서 확인하므로 이슈에 반복 체크하지 않는다.

추가 사항은 필요한 내용만 쓰고 없으면 `없음`을 유지한다. 모든 항목을 채우거나 자기 레포 이름을 반복할 필요는 없다. 환경 변수는 이름·용도만 쓰고 비밀번호·토큰 같은 실제 비밀값은 적지 않는다.

### 12.2 기능 이슈 예시

제목: `feat: 회원가입 API 구현`

```markdown
## 담당자
송상진 / @song-sang-jin

## 작업 내용
- [ ] 회원가입 API 구현
- [ ] 이메일 중복 확인
- [ ] 비밀번호 암호화

## 완료 기준
- [ ] 정상 입력으로 가입할 수 있다.
- [ ] 중복 이메일의 가입을 거부한다.
- [ ] 비밀번호가 암호화되어 저장된다.

## 추가 사항 (선택)
없음
```

### 12.3 버그 이슈 예시

제목: `fix: 중복 이메일 가입 처리 오류 수정`

```markdown
## 담당자
송상진 / @song-sang-jin

## 문제와 재현 방법
발생하는 문제: 같은 이메일로 가입하면 의도한 오류 대신 서버 오류가 발생한다.

재현 순서:
1. 테스트 계정으로 가입한다.
2. 같은 이메일로 다시 가입 요청을 보낸다.

예상 결과: API 명세에 정한 중복 가입 오류 응답
실제 결과: 서버 오류 응답

## 완료 기준
- [ ] 중복 이메일 요청에 명세대로 응답한다.
- [ ] 새로운 이메일의 정상 가입은 유지된다.

## 추가 사항 (선택)
관련 API: 실제 회원가입 API 경로 또는 명세 링크
```

이 예시는 작성 방식 설명이며, 현재 발생이 확인된 버그가 아니다. 실제 버그 등록 시 재현 결과로 수정한다. 다른 담당자의 작업은 해당 담당자의 이름과 실제 GitHub 아이디를 적는다.

### 12.4 문서·설정 및 AI 작업

문서 이슈 제목 예시: `docs: AI 오류 응답 설명 보완`

```markdown
## 담당자
송상진 / @song-sang-jin

## 작업 내용
- [ ] AI 오류와 공개 API 오류의 대응 관계 설명
- [ ] 근거 부족 응답과 시스템 장애의 차이 설명

## 완료 기준
- [ ] 실제 API 계약과 문서 설명이 일치한다.
- [ ] 문서 링크가 정상적으로 열린다.

## 추가 사항 (선택)
AI 담당자와 오류 의미 확인 필요
```

유광민의 AI 작업은 `유광민 / @nmj05172`를 담당자에 적고 같은 양식을 사용한다. 예를 들어 공시 출처 연결을 구현한다면 작업 내용에는 구현 범위를, 완료 기준에는 출처 식별자와 근거 부족 응답 등 확인할 결과를 적는다. 백엔드도 함께 바뀌는 경우에만 추가 사항에 관련 이슈·PR과 적용 순서를 기록한다.

### 12.5 브랜치·커밋·머지 흐름

예를 들어 현재 레포의 실제 이슈 번호가 #42라면:

```text
이슈 #42 등록
→ 최신 dev에서 feat/42-signup 생성
→ 구현·테스트
→ feat: 회원가입 API 구현 커밋 (본문 Refs #42)
→ dev 대상 PR 작성
→ CI 통과·회의 공유·대화 해결
→ 작성자도 Squash and merge 가능
```

작업은 한 목적에 집중하되 이슈 하나를 여러 PR로 나누거나, PR 하나에 관련 이슈 여러 개를 연결할 수 있다. GitHub 승인 리뷰는 필수가 아니다. Squash할 때 최종 변경 내용을 하나의 커밋 제목·본문으로 정리하며 중간 커밋 메시지를 그대로 모두 나열할 필요는 없다.

### 12.6 PR 작성 예시

제목: `feat: 회원가입 API 구현` / base: `dev` / 작업 브랜치: `feat/42-signup`

다음 검증 결과는 작성 예시다. 실제 실행한 결과로 바꾸고, 미실행이면 이유와 확인하지 못한 범위를 기록한다.

```markdown
## 변경 내용
- 회원가입 API 구현
- 이메일 중복 검사와 비밀번호 암호화 적용

## 관련 이슈
Closes #42
Refs #35

## 검증 결과
- 회원가입 성공·중복 이메일 테스트 작성 및 통과
- API 직접 호출로 정상 가입과 중복 이메일 거부 확인

## 추가 사항 (선택)
없음
```

- `Closes`: 이번 PR로 완료하는 이슈. 기본 브랜치 dev로 머지되면 해당 이슈 자동 종료.
- `Refs`: 관련되거나 일부만 작업한 이슈. 자동 종료하지 않음.
- 완료 이슈와 참조 이슈를 함께 여러 개 적을 수 있다. 같은 이슈에 두 키워드를 반복할 필요는 없다.
- 브랜치의 이슈 번호를 본문에 포함한다. 다른 레포 이슈는 `조직/레포#번호` 또는 전체 URL로 작성한다.
- 다른 레포 PR·DB 변경·환경 변수·배포 순서 등은 추가 사항에 필요할 때만 기록한다.

검증 결과에는 자동 테스트뿐 아니라 API 직접 호출·서버 상태 확인·문서 미리보기 등 실제 확인한 방법과 결과를 적는다. `git diff --check`는 공백 등 형식 검사이며 기능 동작 검증을 대신하지 않는다. 필요한 검증이 미완료면 완료했다고 쓰거나 바로 머지하지 않는다.

### 12.7 현재 CI가 자동으로 검사하는 범위

2026-10-25 확인한 각 레포 dev의 `.github/workflows` 기준이다. 이 문서의 설계·계약·통합 검증 항목이 모두 CI로 구현되어 있다는 뜻은 아니다.

| 검사 | 실행 조건 | 자동으로 확인하는 내용 |
| --- | --- | --- |
| 세 레포 Conventions / conventions | PR 생성·제목/본문 수정·커밋 추가·재오픈·Ready 전환 | PR 제목 형식, 브랜치 이름 형식, 본문의 브랜치 이슈 번호 |
| 백엔드 Backend CI / backend | push, pull_request | Java 21에서 `./gradlew --no-daemon check bootJar`로 테스트·검사와 실행 JAR 생성 |
| AI AI CI / ai | push, pull_request | Python 3.12, uv 0.8.22에서 `uv sync --locked`, `uv run --locked ruff check .`, `uv run --locked pytest` |
| 웹 | PR 관련 위 이벤트 | conventions만 있음. 프론트 빌드·테스트는 아직 없음 |

형식 검사 규칙은 다음 세 가지다.

1. **PR 제목**: `type: 요약` 또는 `type(scope): 요약`. 제목 유형은 feat, fix, refactor, docs, test, chore, ci, perf, style, revert이며 scope는 영문 소문자·숫자·하이픈이다. 호환성 파괴 표기 `!`도 허용한다.
2. **브랜치**: `type/이슈번호-영문소문자요약`. 브랜치 유형은 feat, fix, refactor, docs, test, chore, ci, perf, hotfix이며 이슈 번호는 앞자리 0 없는 양의 정수다. 요약은 영문 소문자·숫자와 단어 사이 하이픈을 사용한다. 제목과 브랜치의 허용 유형 목록은 일부 다르다.
3. **본문 연결**: 브랜치에서 추출한 `#이슈번호`가 본문에 있어야 한다. Closes나 Refs 단어 자체는 검사하지 않으며, 다른 이슈를 함께 연결해도 된다.

이슈 등록에는 CI가 없다. 이슈 폼은 필수 입력란이 비었는지만 확인한다. 현재 conventions는 이슈의 실제 존재 여부·본문 내용의 정확성·담당자·커밋 메시지·검증 결과·회의 공유 여부를 검사하지 않는다. PR base도 이 형식 검사 대상은 아니므로 dev인지 확인한다.

CI는 PR 생성을 막는 것이 아니라 검사 결과를 남긴다. 필수 검사에 실패하면 머지가 제한된다. 두 워크플로는 별도이므로 제목 검사가 실패해도 빌드 검사는 독립적으로 실행될 수 있다. 서비스 CI는 push와 PR에서 각각 실행되어 같은 커밋에 결과가 두 개 보일 수 있다. 제목·본문만 수정하면 conventions는 다시 실행되지만 서비스 빌드는 그 이벤트만으로 다시 실행하지 않는다.

## 13. 회의 기록과 일정 관리

- 팀 공통 게시판: [백엔드 Discussions](https://github.com/investlab-team/investlab-backend/discussions). Meetings는 회의록, Technical Discussion은 기술 논의다. 회의록의 이슈 연결은 선택 사항이다.
- 일정: [InvestLab 개발 일정](https://github.com/orgs/investlab-team/projects/2). 전체 작업·진행 보드·로드맵으로 같은 작업을 본다.
- Project에는 이슈를 작업 단위로 추가하고 담당·상태·시작일·목표일을 관리한다. 같은 작업의 PR을 중복 항목으로 추가할 필요는 없다.
- 문서는 `investlab-backend/docs`를 기준으로 관리한다. 최상위에 중복 문서를 별도로 유지하지 않는다.

### 13.1 주간회의 작성 방법

Meetings의 새 글은 `[주간회의] YYYY-MM-DD` 제목으로 작성한다. 회의 일시는 `2026-10-25 16:00`처럼 날짜와 시간만 적는다. 기존 게시글은 새 템플릿을 머지해도 자동 변경되지 않는다.

1. 회의 전: 각자 이번 주 완료·진행 내용과 문제·시도한 방법·해결 제안을 적는다.
2. 회의 중: 도움이 필요한 부분과 제안을 논의한다. 문제가 없으면 `없음`으로 남긴다.
3. 회의 후: 합의한 해결 방향과 담당자, 다음 주 할 일·목표일을 정리한다. 실제 개발 작업은 이슈·Project에도 반영한다.

아래는 작성 방식 예시이며 실제 진행 결과가 아니다. 폼에는 세 사람의 틀이 모두 제공되므로 각자 해당 부분을 채운다.

```markdown
제목: [주간회의] 2026-10-25

### 회의 일시
2026-10-25 16:00

### 참석자
- 송상진
- 박진호
- 유광민

### 이번 주 진행 내용
## 송상진 (백엔드)
- 완료한 일: 로컬 H2 실행 설정 정리
- 진행 중인 일: 로그인 흐름 설계
## 박진호 (백엔드)
- 완료한 일: 시장 정책 요구사항 확인
- 진행 중인 일: 비즈니스 로직 구현
## 유광민 (AI)
- 완료한 일: 공시 API 응답 구조 확인
- 진행 중인 일: 수집 데이터 저장 구조 설계

### 문제·막힌 부분과 해결 제안
## 송상진
- 문제 또는 막힌 부분: AI 요청 실패 시 응답 기준이 정해지지 않음
- 시도한 방법·확인한 내용: 현재 API 명세 확인
- 해결하고 싶은 방향·도움 요청: 유광민과 오류 응답 형식 합의
## 박진호
- 없음
## 유광민
- 없음

### 회의에서 정한 해결 방향·결정 사항
- 결정한 내용: 백엔드·AI 오류 응답 초안을 함께 검토한다.
- 담당자·추가 확인할 내용: 송상진·유광민 / 각 서버 오류 상황 정리
- 보류한 내용: 없음

### 다음 주 계획
## 송상진 (백엔드)
- [ ] 로그인 API 설계와 이슈 등록 / 목표일: 10월 30일
## 박진호 (백엔드)
- [ ] 시장 정책 로직 구현·검증 / 목표일: 10월 30일
## 유광민 (AI)
- [ ] 공시 데이터 수집 초안 구현 / 목표일: 10월 30일

### 다음 회의·참고 자료 (선택)
다음 회의: 2026-11-01 16:00
참고 링크: 없음
```

주간 진행·일정·막힌 부분 공유는 Meetings에 남긴다. 특정 기술 선택에 추가 비교나 댓글 논의가 필요하면 Technical Discussion에 별도 글을 작성하고 회의록에 링크한다. 회의에서 바로 결정한 내용까지 두 게시판에 중복 작성할 필요는 없다.
