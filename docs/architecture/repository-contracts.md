# InvestLab 레포 간 협업 규약

작성일: 2026-10-10 (KST)

상태: 3개 레포 설계를 위한 규약 초안. 구체적인 제한시간·배포 환경·도구 버전은 착수 시 확정한다. 기존 공개 API 명세의 정책은 유지하며 내부 AI 계약은 신규 작성 대상이다.

## 1. 책임과 기준 위치

### 1.1 팀 담당

| 이름 | 담당 | 현재 분담 상태 |
| --- | --- | --- |
| 송상진 | 백엔드, 명세·설계 문서, 인프라 | A: 회원·계좌·랭킹·관심·AI 연동 |
| 박진호 | 백엔드 | B: 주문·체결·잔고·초기화·시세 |
| 유광민 | AI | C: AI 구현·수집·RAG 담당 |

프론트 담당과 기술은 미정이다. 확정된 A/B/C 기능 담당은 [API 명세 및 담당 표](../api/README.md)를 따른다. 권장·후속 기능과 담당 변경은 이슈에서 합의하고 표를 함께 갱신한다. 담당자는 구현·기준 유지 책임자이며 회의 설명과 CI 통과 후 자기 PR을 머지할 수 있다.

### 1.2 기준 위치·담당·검토

| 대상 | 기준 위치 | 책임 담당 | 변경 검토 |
| --- | --- | --- | --- |
| 공개 API 명세 | investlab-backend/contracts/public-api.yaml | 송상진 | 작성자 외 백엔드 담당, 향후 영향받는 프론트 담당 |
| 내부 AI API 명세 | investlab-ai/contracts/internal-ai-api.yaml | 송상진: 명세 관리 / 유광민: AI 구현 일치 | 작성자 외 백엔드·AI 영향 담당 |
| 전체 아키텍처·협업 규약·원본 명세 | investlab-backend/docs | 송상진 | 박진호 또는 유광민, 변경 영역에 따라 검토 |
| 인프라·통합 실행·배포 설정 | backend/infra 및 각 레포 CI·배포 파일 | 송상진 | 작성자 외 영향받는 담당 |
| 백엔드 구현·거래 DB 마이그레이션 | investlab-backend | 송상진·박진호 | 상대 백엔드 담당 |
| AI 구현·기업분석 DB 마이그레이션 | investlab-ai | 유광민 | 송상진 또는 박진호, AI 계약·검증 결과 포함 |
| 앱별 의존성 | 해당 앱 레포 | 백엔드: 송상진·박진호 / AI: 유광민 | 작성자 외 담당 |
| Secret·운영 환경 설정 | 레포별 배포 환경 | 송상진, AI 필요 설정은 유광민과 협의 | 값 공개 없이 적용·권한·교체 방식 검토 |

GitHub 계정명은 아직 받지 않았으므로 CODEOWNERS와 실제 권한 설정에는 실명 대신 계정명을 확인하여 반영한다. 관련 레포의 읽기·리뷰·머지 권한도 이 규칙을 수행할 수 있게 설정해야 한다.

여기서 계약은 URL, 요청·응답 필드, 타입, 필수 여부, 상태·오류, 인증, 동작 의미까지 포함한 약속이다. Java 엔티티·Python 모델·향후 프론트 타입을 동일한 소스 파일로 공유할 필요는 없다.

소비자는 제공자 레포의 특정 태그나 커밋에서 계약을 가져온다. 브랜치 최신 파일을 매번 가져오지 않는다. 별도 패키지 레지스트리 없이 시작할 수 있으며, 비공개 레포의 CI 접근은 최소 읽기 권한으로 설정한다. 생성 클라이언트·타입을 커밋한다면 생성 명령과 기준 계약 커밋을 함께 기록한다.

## 2. 공통 데이터 표현

| 항목 | 규칙 |
| --- | --- |
| 공개 경로 | 기존 /api/v1 계약 유지 |
| 내부 AI 경로 | /internal/v1을 제안. 실제 엔드포인트는 내부 계약 작성 때 확정 |
| 직렬화 | application/json, UTF-8, JSON 필드는 camelCase |
| ID | UUID 문자열. companyId, instrumentId, documentId의 발급 책임을 명시 |
| 금액·가격·수량·비율 | Decimal 문자열. Java BigDecimal·Python Decimal 사용, JS 부동소수점 계산으로 거래값을 확정하지 않음 |
| 수익률 | 퍼센트 단위. "0.2"는 0.2%이며 20%가 아님 |
| 시각 | ISO 8601 UTC(Z). 날짜 경계·초기화 일자는 Asia/Seoul |
| 날짜 | YYYY-MM-DD. 회계연도·분기·보고서 기간은 별도 필드 |
| 누락 | null, 필드 생략, 0의 의미를 구분. 시세·근거 부족을 0으로 대체하지 않음 |
| 상태 | 계약에 정의된 enum 사용. 추가 시 소비자의 미지 상태 처리를 검토 |
| 목록 | 기존 cursor·limit·nextCursor와 정렬 규칙 유지 |

재무 값은 단위·통화·기간·연결/별도 기준을 함께 전달한다. ROA·ROE 등 계산식과 분모 기준은 기존 P-07 제안의 승인 후 고정한다.

## 3. 공개 응답과 오류

기존 API 명세의 형식을 유지한다.

```json
{
  "data": {},
  "meta": { "requestId": "요청 식별자" }
}
```

```json
{
  "error": {
    "code": "DATA_UNAVAILABLE",
    "message": "데이터를 조회할 수 없습니다.",
    "details": []
  },
  "requestId": "요청 식별자"
}
```

빈 목록, 리소스 없음, 권한 거부, 가격 지연, 외부 장애를 구분한다. 기존 400/401/403/404/409/422/429/503 의미를 유지한다. 내부 AI 실패는 백엔드에서 공개 오류로 변환하며 내부 URL·스택·공급자 비밀 정보를 반환하지 않는다. 로그인 갱신 실패나 주문 재시도 같은 프론트 행동도 오류 코드별로 합의한다.

## 4. 인증과 권한

- 백엔드 로그인 인증은 Spring Security + JWT로 확정한다. 액세스 토큰은 JWT이며 공개 API에 Authorization: Bearer로 전달한다. 리프레시는 기존 명세에 따라 HttpOnly 쿠키로 전달하고 서버에서 유효성·폐기를 관리한다. 리프레시 토큰 자체의 JWT/불투명 형식은 별도 결정한다.
- JWT 서명·만료·issuer·audience를 검증하고 허용 알고리즘을 고정한다. 서명키는 Secret으로 관리하며 토큰·비밀번호를 로그에 남기지 않는다. 액세스 1시간·리프레시 14일은 기존 명세의 제안값이며 구현 전에 승인한다.
- 쿠키 갱신·로그아웃은 CSRF 토큰과 Origin을 검사한다. 도메인·CORS·쿠키 정책은 배포 환경과 함께 확정한다.
- 초기 운영은 하나의 공개 도메인에서 웹과 /api를 제공하는 구조를 추천한다. 프론트가 별도 배포되어도 리버스 프록시로 같은 사이트를 제공할 수 있다. 도메인을 분리한다면 쿠키 설계를 재검토한다.
- 본인 계좌·주문 권한은 백엔드가 검사한다. 로그인 여부만으로 소유권을 인정하지 않는다.
- 내부 AI API는 백엔드용 서비스 인증과 네트워크 접근 제한을 적용한다. 사용자 액세스 토큰을 무조건 전달하지 않는다.
- Secret 값은 레포별 배포 환경에 저장한다. 서버 간 공유 인증 값은 두 배포 환경에서 일치시켜야 하지만 Git 문서에는 실제 값을 적지 않는다.

## 5. 내부 AI 계약에서 반드시 정할 필드

아래는 계약 설계 항목이며 실제 API 구현이나 기존 명세에 추가된 확정 필드가 아니다.

| 요청 항목 | 합의 내용 |
| --- | --- |
| 요청 ID | 백엔드가 발급하고 AI·로그로 전달 |
| 질문 | 길이·허용 형식·빈 입력 처리 |
| 기업·기간 문맥 | 식별자·회계기간 기준. 사용자 입력과 서버 검증 결과 구분 |
| 대화 문맥 | 이전 대화를 지원할지와 길이·보존·권한 기준 |
| 개인화 문맥 | 1차 개인 계좌 도구는 후속 범위. 추가 시 본인 권한 확인 후 최소 데이터만 전달 |

| 응답 항목 | 합의 내용 |
| --- | --- |
| 답변 | 핵심 설명과 정형 수치·단위·기간 |
| 결과 상태 | 정상·추가 질문 필요·근거 부족을 구분. 도구 장애는 오류로 구분 |
| 출처 | 공시·재무 식별자, 제목, 공시일, 버전, 청크 또는 재무 항목 근거 |
| 계산 | 지표, 공식, 입력 값, 기간·회계 기준 |
| 오류 | 코드, 재시도 가능 여부. 공개 API 매핑은 백엔드 책임 |

근거 부족은 시스템 장애와 다르다. 근거 부족을 성공한 분석처럼 표현하거나 도구 장애를 근거 부족으로 숨기지 않는다. 출처 식별자는 이후 원문을 확인할 수 있도록 안정적으로 유지한다.

## 6. 데이터 소유권과 식별자

백엔드는 사용자·계좌·거래·종목·랭킹·관심목록과 사용자 AI 답변 이력을 소유한다. AI는 기업·공시·재무·청크·임베딩·수집 작업을 소유한다. 상대 서비스 DB를 직접 변경하지 않는다.

companyId는 AI 데이터 영역에서 발급하고, 백엔드의 종목 매핑은 AI의 기업 식별 정보를 검증한 뒤 저장하는 안을 제안한다. instrumentId는 백엔드가 발급한다. 공시 정정은 문서 버전으로 구분하며 기존 답변의 근거를 새 버전으로 조용히 바꾸지 않는다.

종목·기업 연결과 답변 출처의 서비스 간 ID는 서비스 독립성을 위해 DB 간 FK를 사용하지 않고 계약과 동기화 검증으로 관리한다. PostgreSQL의 두 DB에 각각 전용 계정·마이그레이션 책임을 둔다. 기존 ERD를 수정해 ID 발급 책임, 누락 처리, 삭제·보존 규칙을 명시한 후 구현한다.

## 7. 호출 제한시간·재시도·추적

- 백엔드의 X-Request-Id를 AI에 전달하고 양쪽 로그에서 같은 ID로 조회한다. 브라우저 요청 ID 입력은 검증하거나 서버에서 교체한다.
- AI 최대 처리시간, 백엔드 내부 호출 제한시간, 공개 진입점 제한시간, 프론트 대기시간을 일관되게 정한다. AI 처리시간 < 백엔드 제한시간 < 진입점·클라이언트 대기시간 순서를 기준으로 여유 시간을 둔다.
- AI 동시 요청 수·질문 길이·LLM 토큰·사용자 호출 한도를 정한다. 정확한 값은 표본 질의의 지연·비용 측정 후 확정한다.
- LLM 비용과 답변 이력 중복을 방지하기 전에는 AI 분석 POST를 자동 재시도하지 않는다. 제한시간 초과가 작업 중단을 보장하지 않음을 고려한다.
- 계좌 생성·주문·초기화는 기존 Idempotency-Key 규칙을 유지한다. 같은 키의 재사용·충돌·진행 중 상태를 모든 소비자가 동일하게 처리한다.
- 질문 전문·개인 정보·토큰은 무조건 로그에 남기지 않는다. 필요한 추적 정보와 답변 보존 정책을 구분한다.

## 8. 레포 간 변경 절차

1. 이슈에 영향받는 레포·API·데이터·배포 순서를 기록한다.
2. API 제공자 레포에서 계약과 예시를 먼저 검토한다. 관련 소비자 담당자가 참여한다.
3. 제공자와 소비자 PR을 상호 링크한다. 소비자는 합의한 계약 태그·커밋을 고정한다.
4. 제공자 응답이 계약에 맞는지 검사하고 소비자가 처리하는 정상·빈값·근거 부족·오류 사례를 확인한다.
5. 선택한 세 앱 버전으로 스테이징 통합 검증을 수행한다.
6. 호환성을 유지하는 순서로 배포하고 실제 배포 버전 조합을 기록한다.

필드 삭제, 필수 요청값 추가, 타입·단위·상태 의미 변경은 호환성 파괴로 취급한다. 선택 응답 필드 추가도 소비자가 미지 필드를 허용하는지 검증한다. 앱 버전과 API 버전은 별개이며, 단순 앱 배포마다 /v2를 만들지 않는다.

예: AI 답변에 새 선택 출처 필드를 추가한다면 AI가 기존 백엔드와 호환되는 응답을 먼저 제공 → 백엔드가 이를 공개 응답에 연결 → 프론트가 출처 UI를 사용한다. 필드를 교체할 때는 일정 기간 신·구 필드를 함께 지원하고 소비자 전환을 확인한 뒤 구형 필드를 제거한다.

## 9. CI·통합 실행·릴리스

각 레포 CI는 해당 언어의 빌드·검사와 제공 계약 또는 소비 계약의 검증을 수행한다. 모든 PR에서 세 레포 최신 브랜치를 무조건 조합하지 않는다. 계약 변경 PR은 관련 소비자와 검증할 커밋을 지정한다.

전체 통합 실행은 백엔드의 infra/compose.integration.yaml을 기준으로 한다. 기본 실행은 버전이 고정된 이미지를 사용하고, 로컬 개발 앱만 소스 실행으로 대체할 수 있게 한다. DB·Redis·AI·백엔드의 준비 상태와 마이그레이션 순서를 정의한다.

backend/docs/releases에는 다음 버전 조합을 기록한다.

```yaml
# 형식 예시이며 실행 가능한 배포 파일이 아님
webCommit: <검증한 커밋>
backendCommit: <검증한 커밋>
aiCommit: <검증한 커밋>
publicContractCommit: <백엔드 계약 커밋>
internalAiContractCommit: <AI 계약 커밋>
backendImage: <불변 태그 또는 digest>
aiImage: <불변 태그 또는 digest>
webArtifact: <프론트 배포 식별자>
```

실제 배포는 latest에 의존하지 않는다. 앱별 릴리스 번호는 같을 필요가 없다. DB 변경은 확장 → 앱 전환 → 구형 구조 제거 순서로 호환성을 유지하고, 되돌릴 수 있는 앱 버전과 DB 변경의 관계를 확인한다.

공통 핵심 검증: 로그인·갱신, 주문 접수·체결·초기화, 재무 질의·계산·공시 출처, 근거 부족, AI 장애 시 거래 기능 정상 동작. 단위 검사만으로 레포 간 호환성을 확인한 것으로 간주하지 않는다.

## 10. Git 컨벤션과 PR 규칙

### 10.1 브랜치

세 레포의 기본·개발 통합 브랜치는 `dev`다. 최신 `dev`에서 이슈별 작업 브랜치를 만들고 PR의 base는 `dev`로 설정한다. `dev`와 `main`에 직접 push하지 않는다. `main`은 릴리스 기준으로 보존하며 팀이 릴리스 범위·시점을 합의한 뒤 별도 PR로 반영한다. 일상 기능 PR은 `main`으로 보내지 않는다.

형식: `<type>/<레포 내 이슈번호>-<영문-kebab-case>`

```text
feat/12-jwt-login
fix/18-order-reservation
refactor/23-account-validation
docs/7-system-architecture
chore/9-ci-setup
hotfix/31-token-validation
```

feat, fix, refactor, docs, test, chore, ci, perf, hotfix를 사용한다. 이슈 번호는 레포별이므로 상대 레포 이슈는 `조직/레포#번호` 또는 URL로 참조한다. 짧은 기능 브랜치를 사용하며 완료된 브랜치는 머지 후 삭제한다.

### 10.2 커밋 메시지

형식: `<type>(<scope>): <한국어 또는 영어 변경 요약>`

scope는 선택이며 auth, trading, market, research, rag, ingestion, infra, docs 등 실제 변경 영역을 적는다. 이 목록은 담당자 배정이 아니다.

| type | 용도 |
| --- | --- |
| feat | 사용자·서비스 기능 추가 |
| fix | 오류 수정 |
| refactor | 동작 의미를 유지하는 구조 개선 |
| docs | 문서·명세 수정 |
| test | 테스트 추가·수정 |
| chore | 의존성·도구·관리 작업 |
| ci | CI·배포 파이프라인 변경 |
| perf | 성능 개선 |
| style | 동작 변화 없는 포맷 수정 |
| revert | 기존 변경 되돌림 |

```text
feat(auth): JWT 로그인 API 추가
fix(trading): 동시 주문의 예약금 초과 방지
docs(architecture): PostgreSQL 데이터 소유권 명시
ci(backend): Gradle 빌드 검사 추가
```

관련 변경만 한 커밋에 담고 `수정`, `작업 중`, `최종` 같은 모호한 요약을 사용하지 않는다. 본문이 필요하면 변경 이유와 영향·검증을 기록한다. 각 커밋 본문에는 `Refs #12` 형식으로 해당 레포 이슈를 연결하고 PR 본문에도 연결한다. 상대 레포 이슈는 전체 레포 이름 또는 URL을 사용한다. 의도적인 호환성 파괴는 `feat(api)!: ...`와 `BREAKING CHANGE:` 설명으로 표시하되, 배포 전환 계획을 반드시 포함한다.

### 10.3 이슈와 PR

**모든 변경은 작업 전에 해당 레포에 이슈를 등록한다. 기능·버그·문서·명세·인프라·CI·긴급 수정에도 예외 없이 적용한다.** 이슈에는 작업 내용·완료 기준을 필수로 적고 참고 사항은 필요할 때만 작성한다. 담당자는 폼의 담당자 입력란에 이름 / @아이디로 기록하고 일정은 Project에서 관리한다. 목적은 작업 내용에 필요할 때 한 문장으로 적는다. 브랜치 이름에 이슈 번호를 넣고, 각 커밋 본문에 `Refs #12`처럼 연결하며, PR 본문에도 관련 이슈를 연결한다. 같은 목적의 기존 이슈가 있다면 재사용하고 PR에 설명한다. 기능별 담당은 API 담당 표를 기준으로 이슈에 기록하며, 분담 변경은 송상진·박진호가 합의해 문서에도 반영한다. PR은 한 목적 중심으로 만들고 미완료는 Draft로 표시한다.

PR 제목은 커밋 형식과 동일하게 작성한다. PR 본문에 다음을 기록한다.

```markdown
## 변경 목적과 결과

## 관련 이슈·레포 PR

## API·DB·인증 변경

## 검증 결과

## 배포 순서·호환성·롤백 영향
```

영향 없는 항목은 해당 없음으로 표시한다. 예: 이슈 `#12` 등록 → `feat/12-jwt-login` 브랜치 생성 → `feat(auth): JWT 로그인 API 추가` 커밋(본문 `Refs #12`) → PR 본문에 `Closes #12` → 회의에서 설명 후 작성자 머지. `feat` 등 유형 라벨은 이슈 분류용이고 `v1.0.0` 같은 Git 릴리스 태그와 다르다.

이슈 종료 키워드 `Closes #12`는 해당 레포의 이슈를 실제 완료하는 경우에만 사용한다. 상대 레포 작업이 남아 있으면 연결하고 완료 상태를 구분한다.

### 10.4 리뷰·머지 — 모든 PR에 적용

작성자는 회의에서 PR 변경 내용·검증 결과·영향을 설명하고 논의 사항을 반영한 뒤 자신의 PR을 직접 머지할 수 있다. GitHub 승인 리뷰는 필수가 아니다.

- 모든 변경은 이슈·브랜치·PR로 연결하고 필수 CI를 통과해야 한다.
- API·DB·인증·인프라 변경은 영향받는 담당자와 확인한다.
- 미해결 대화를 해결한 뒤 Squash and merge한다. 최종 메시지는 PR 제목 컨벤션을 따른다.
- dev·main 직접 push·force push·삭제는 금지한다. 오류는 fix/revert PR로 수정한다.

### 10.5 GitHub 보호 설정

dev와 main의 PR 필수·필수 CI·각 대상 브랜치 최신 기준 검사·대화 해결·force push 및 삭제 금지는 유지한다. 필수 승인 인원과 자기 PR 머지 제한은 적용하지 않는다. CODEOWNERS는 계정 확인 후 담당 안내 용도로 검토하며 필수 승인 조건으로 사용하지 않는다.

근거: [GitHub 필수 리뷰](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews), [Ruleset 규칙](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

### 10.6 릴리스와 제외 파일

레포별 릴리스 태그는 `v<major>.<minor>.<patch>`를 사용한다. 앱 태그와 API 경로 버전은 구분하며 세 레포 태그 번호를 맞출 필요는 없다. 배포 조합은 9절 기준으로 기록한다.

실제 `.env`, 키·토큰·인증서 개인키, `.venv`, `node_modules`, 빌드 결과, 개인 IDE 설정은 커밋하지 않는다. Gradle Wrapper, uv.lock 및 추후 선택할 프론트 lockfile은 커밋한다. 이미 적용된 DB 마이그레이션 파일을 임의 수정하지 않고 신규 마이그레이션으로 변경한다.

완료 조건은 해당 레포 코드 머지뿐 아니라 필요한 상대 레포 전환과 통합 검증까지 포함한다.

참조: [시스템 아키텍처](system-architecture.md). 이 문서는 규약이며 GitHub 보호 설정·CODEOWNERS·CI·머지 App을 실제 생성하거나 적용한 결과는 아니다.

## 11. 현재 기술 결정 반영

backend는 Java 21 LTS(Eclipse Temurin) + Spring Boot 4.1.1 + Gradle을 사용한다. Java 주 버전과 Spring Boot 버전은 확정이며 개발·CI·컨테이너에 동일하게 적용한다. Gradle Wrapper는 공식 Initializr가 제공한 9.7.1로 고정한다. JDK 패치 버전은 보안 업데이트에 따라 관리한다. RDB는 PostgreSQL 16을 사용한다. AI는 Python 3.12 + FastAPI + uv를 추천하며 상세 라이브러리는 시스템 아키텍처 1.3절을 따른다.

프론트 기술·배포는 미정이며 백엔드 먼저 구현한다. web의 TypeScript 클라이언트·Node CI·독립 배포는 아직 확정하지 않는다. 별도 프론트 선택 시 기존 3레포 규약을 적용한다. Thymeleaf 선택 시 화면을 백엔드 templates/static에 포함하고 web 레포와 3앱 릴리스 조합은 재검토한다. 백엔드 로그인 JWT 선택은 유지한다. Thymeleaf 선택 시 브라우저의 JWT 전달·보관 방식과 서버 렌더링·CSRF 처리를 별도로 설계한다. 백엔드 API와 AI의 내부 계약은 화면 방식과 관계없이 유지한다.

## 12. 이슈부터 PR까지 작성 실습

이 절은 세 레포 공통 가이드다. 아래 번호 `42`, `43`, `44`는 설명용이며, 반드시 **작업하는 레포에서 실제 등록한 이슈 번호**로 바꾼다. 예시를 그대로 제출하지 말고 실제 작업·검증 결과로 수정한다.

### 12.1 간소화한 이슈 작성 기준

기능 작업과 설정·문서 작업은 **담당자·작업 내용·완료 기준** 세 항목이 필수다. 버그 수정은 작업 내용 대신 **문제와 재현 방법**을 필수로 적는다. **추가 사항은 선택**이며 기본값은 `없음`이다. 별도 목적, 검증 계획·배포 영향 필수란, 공통 CI 체크박스는 제거했다. 아래 12.2~12.4의 상세 예시는 필요한 내용을 참고하는 자료이며 모든 항목을 채우라는 뜻이 아니다.

| 항목 | 작성 기준 |
| --- | --- |
| 작업 내용 | 앞으로 구현·수정할 일을 체크리스트로 작성한다. |
| 완료 기준 | 결과를 확인하면 체크할 구체적인 동작·조건을 작성한다. 테스트 코드나 직접 API 확인 등 적절한 방법으로 검증한다. |
| 문제와 재현 방법 | 버그의 증상·재현 순서·예상 결과·실제 결과를 기록한다. |
| 추가 사항 (선택) | 관련 API·선행 이슈·다른 레포 작업·DB나 환경 변수 변경 등 필요할 때만 적는다. 자신의 레포 이름은 반복하지 않는다. |

담당자는 폼에 **이름 / @아이디**로 작성하고 일정은 **Project**에서 관리한다. 이름 입력이나 @멘션은 GitHub Assignees를 자동 지정하지 않으며, Project의 Assignees 열에도 자동 반영되지 않는다. 그 기능이 필요할 때만 Assignees를 별도로 지정한다. 완료 기준은 이슈 등록 시 미체크로 두고 구현·검증 후 담당자가 직접 체크한다. CI 결과는 PR에서 확인하며 이슈 본문에서 반복 체크하지 않는다. PR 템플릿·제목·브랜치·이슈 연결 및 CI 규칙은 그대로 유지한다.

작성 예시 — 제목 `feat: 회원가입 API 구현`:

```markdown
## 담당자
송상진 / @song-sang-jin

## 작업 내용
- [ ] 회원가입 API 구현
- [ ] 이메일 중복 확인
- [ ] 비밀번호 암호화

## 완료 기준
- [ ] 정상 입력으로 가입할 수 있다.
- [ ] 중복 이메일의 가입을 거부한다.
- [ ] 비밀번호가 암호화되어 저장된다.

## 추가 사항
없음
```

추가 사항이 없다면 `없음`을 그대로 둔다. 기능은 `feat:`, 버그는 `fix:`, 설정은 `chore:`로 제목이 시작하며 문서 작업은 `docs:`로 변경할 수 있다. 날짜와 계정은 실제 담당자와 팀 일정에 맞춰 정한다.

### 12.2 기능 이슈 예시 — A 송상진의 로그인 구현

제목: `feat: JWT 로그인 API 구현`

아래 각 내용을 대응하는 폼 입력란에 나눠 넣는다. API 응답과 오류의 세부 기준은 실제 공개 API 명세를 따른다.

```markdown
담당자: 송상진 / @song-sang-jin

## 목적과 변경 내용
회원이 로그인하고 인증이 필요한 API를 이용하도록 로그인 기능을 구현한다.
- [ ] 명세에 정의된 로그인 요청 검증
- [ ] 자격 증명 확인과 JWT 발급
- [ ] 인증 실패 응답 구현

## 완료 기준
- [ ] 유효한 자격 증명으로 로그인하면 명세에 맞는 응답을 반환한다.
- [ ] 잘못된 자격 증명은 명세에 정의된 오류로 응답한다.
- [ ] 발급 토큰으로 보호 API를 호출할 수 있다.
- [ ] 비밀번호와 토큰을 로그에 남기지 않는다.
- [ ] 관련 테스트와 backend CI를 통과한다.

## 관련 레포·API·이슈
관련 레포: 현재 없음. 프론트 연결 시 별도 이슈 등록
관련 API: contracts/public-api.yaml의 로그인·인증 계약
관련 이슈: 해당 없음

## 검증 계획·배포 영향
- [ ] 정상 자격 증명 → 로그인 성공 응답 확인
- [ ] 잘못된 비밀번호 → 인증 실패 응답 확인
- [ ] 만료·변조된 토큰 → 보호 API 접근 거부 확인
환경 변수 변경: JWT 설정 필요 여부를 구현 전 확인
DB 변경·마이그레이션: 구현 범위 확정 후 기록
배포 순서·주의 사항: JWT 설정 적용 후 배포, 실제 Secret은 이슈에 기재하지 않음
```

### 12.3 버그 이슈 예시 — B 박진호의 주문 오류 수정

제목: `fix: 동시 주문에서 예약금 초과 방지`

```markdown
담당자: 박진호 / GitHub 계정 미정

## 목적과 변경 내용
동시 주문 요청이 동일한 가용 현금을 사용하여 예약금이 초과되는 문제를 수정한다.

### 재현 방법
환경: 로컬, 테스트용 계좌와 거래 데이터
1. 가용 현금보다 두 주문의 합계가 크도록 테스트 계좌를 준비한다.
2. 각각은 가용 현금 이내인 주문 두 건을 동시에 요청한다.
3. 두 주문이 모두 승인되는지 확인한다.

### 예상 결과
명세의 잔고·예약금 정책에 따라 초과 주문을 거부한다.

### 실제 결과
두 주문이 모두 승인되어 가용 현금을 초과한다.

### 오류 로그
테스트 결과와 요청 ID를 첨부한다. 사용자 정보와 토큰은 제거한다.

## 완료 기준
- [ ] 동시 요청에서도 현금·예약금 불변 조건을 유지한다.
- [ ] 단일 정상 주문은 기존대로 처리된다.
- [ ] 동시성 회귀 테스트와 backend CI를 통과한다.

## 관련 레포·API·이슈
관련 레포: 해당 없음
관련 API: 주문 접수 API와 예약금 처리
관련 이슈: 해당 없음

## 검증 계획·배포 영향
- [ ] 동시 주문 요청을 반복하여 초과 승인 여부를 확인한다.
- [ ] 정상 주문·취소·예약금 반환을 확인한다.
환경 변수 변경: 없음
DB 변경·마이그레이션: 잠금·제약조건 설계에 따라 확정 후 기록
배포 순서·주의 사항: 변경된 거래 처리 방식과 롤백 영향을 PR에 기록
```

이 예시는 버그 작성 형식 설명이며, 현재 프로젝트에 해당 버그가 확인되었다는 뜻은 아니다.

### 12.4 문서·설정 이슈와 AI 작업

문서 이슈 제목 예시: `docs: AI 오류 응답 계약 설명 보완`

```markdown
담당자: 송상진 / @song-sang-jin
목적과 변경 내용: 백엔드와 AI 담당자가 동일한 오류 매핑을 구현하도록 계약 설명과 예시를 보완한다.
- [ ] 공개 오류와 내부 오류 매핑표 작성
- [ ] 근거 부족과 시스템 장애 구분 예시 작성
완료 기준:
- [ ] 공개 API 및 내부 AI 계약과 설명이 일치한다.
- [ ] 유광민과 오류 의미를 확인한다.
- [ ] 링크와 문서 PR의 CI를 통과한다.
관련 레포: investlab-ai
관련 API: contracts/public-api.yaml 및 internal-ai-api.yaml
관련 이슈: 실제 AI 이슈 URL 입력. 아직 없으면 미등록이라고 기록
검증 계획: 계약 파일과 매핑표 대조, 링크 확인
환경 변수·DB·배포 변경: 없음
```

C 유광민의 AI 작업도 investlab-ai에서 같은 절차를 따른다. 예를 들어 `feat: 분석 응답에 공시 출처 연결` 이슈를 등록하고, 담당자를 `유광민 / GitHub 계정 미정`으로 작성한다. 완료 기준에는 출처 식별자·근거 부족 응답·내부 AI 계약 일치와 Ruff·pytest 검증을 기록한다. 백엔드 연동이 필요하면 상대 이슈·PR을 전체 URL로 연결하고 배포 순서를 합의한다.

### 12.5 브랜치와 커밋 생성 예시

로그인 이슈가 **현재 레포의 #42로 등록된 경우** 다음을 사용한다. 커밋 명령은 실제 변경 파일을 확인하고 실행한다.

```sh
git switch dev
git pull --ff-only origin dev
git switch -c feat/42-jwt-login
# 구현 후 관련 파일만 git add로 선택한다.
git diff --cached
git commit -m "feat(auth): JWT 로그인 API 구현" -m "Refs #42"
git push -u origin feat/42-jwt-login
```

버그 이슈 #43은 `fix/43-order-reservation`, 문서 이슈 #44는 `docs/44-ai-error-guide`처럼 만든다. 현재 작업이 남아 있으면 먼저 상태를 확인하여 다른 브랜치의 변경과 섞지 않는다. 작업 브랜치에는 영문 소문자·숫자와 단어 사이 하이픈을 사용한다. `dev`나 `main`에서 직접 작업을 push하지 않는다.

### 12.6 PR 작성 예시 — CI 형식 검사 통과 조합

GitHub에서 base를 `dev`, compare를 `feat/42-jwt-login`으로 선택한다. PR 제목: `feat(auth): JWT 로그인 API 구현`.

다음은 구현과 검증이 완료된 상황의 작성 예시다. 테스트를 실행하지 않았다면 통과했다고 적지 말고 미실행·이유를 기록하며, 필요한 검증을 완료한다.

```markdown
## 변경 목적과 결과
회원 로그인과 JWT 발급을 구현했습니다. 인증 실패는 공개 API 계약에 따라 응답합니다.

## 관련 이슈·레포 PR
Closes #42
다른 레포 변경: 해당 없음

## API·DB·인증 변경
공개 로그인 계약에 맞춰 구현했습니다. JWT 검증을 보호 API에 적용했습니다.
DB 변경: 없음 (실제 변경이 있으면 마이그레이션 파일과 내용을 작성)

## 검증 결과
- 정상 로그인·잘못된 자격 증명·만료 및 변조 토큰 테스트 통과
- ./gradlew --no-daemon check bootJar 통과
- GitHub backend 및 conventions 검사 통과

## 배포 순서·호환성·롤백 영향
JWT 설정 적용 후 배포합니다. 실제 값은 GitHub Secret 또는 배포 환경에서 관리합니다.
롤백 영향: 실제 구현과 배포 설정을 기준으로 작성

## 확인
- [x] 작업 전에 이슈를 등록하고 브랜치·커밋·PR에 연결했습니다.
- [x] Secret과 실제 .env를 포함하지 않았습니다.
- [x] 관련 API 계약·문서를 확인하고 필요한 변경을 반영했습니다.
- [ ] 회의에서 변경 내용과 검증 결과를 설명했습니다.
- [x] PR base를 dev로 설정했습니다.
```

회의 설명 항목은 실제 설명 후 체크한다. GitHub 필수 승인 리뷰는 없지만 CI 통과·대화 해결·대상 브랜치 최신 기준 검사 후 머지한다. CI가 통과해도 작업이나 회의 설명이 미완료라면 머지하지 않는다.

### 12.7 현재 CI가 자동으로 검사하는 범위

검사의 기준 파일은 각 레포의 `.github/workflows/conventions.yml`이며 서비스 검사는 `.github/workflows/ci.yml`이다. 다음은 현재 구현된 검사다. 앞 절의 계약 검증·통합 검증은 추가로 수행할 팀 기준이며 모두 자동화된 상태는 아니다.

| 검사 | 실제 기준 |
| --- | --- |
| PR 제목 | `type: 요약` 또는 `type(scope): 요약`. 콜론 뒤 공백과 요약 필요. scope는 영문 소문자·숫자·하이픈. |
| 제목 type | feat, fix, refactor, docs, test, chore, ci, perf, style, revert. `!` 호환성 파괴 표기도 허용. |
| 브랜치 | `type/양의이슈번호-영문소문자숫자-요약`. type은 feat, fix, refactor, docs, test, chore, ci, perf, hotfix. |
| 이슈 연결 | 브랜치에서 추출한 번호의 `#번호`가 PR 본문에 있어야 한다. `feat/42-jwt-login`이면 본문 `Closes #42` 또는 `Refs #42`. |
| 백엔드 | Java 21에서 `./gradlew --no-daemon check bootJar`. |
| AI | Python 3.12에서 `uv sync --locked`, `uv run --locked ruff check .`, `uv run --locked pytest`. |
| 웹 | 현재 conventions만 실행. 프론트 기술 확정 후 빌드·테스트 추가. |

서비스 CI는 push와 pull_request에서 실행하고, conventions는 PR 생성·제목/본문 수정·커밋 추가·재오픈·Ready 상태 전환에서 실행한다. 같은 커밋에 서비스 push/PR 검사가 둘 다 보일 수 있다.

**이슈 내용·실제 존재 여부·담당자·커밋 메시지·체크박스·회의 설명은 현재 conventions에서 자동 검증하지 않는다.** PR base는 이 정규식 검사 대상이 아니므로 직접 `dev`인지 확인한다. 형식 검사는 번호 문자열 연결만 검사하므로 엉뚱한 레포 이슈나 미등록 번호를 넣어 통과시키지 않는다. 코드의 정확성은 테스트와 검토로 확인한다.

`hotfix`는 브랜치 유형으로만 허용되므로 `hotfix/43-token-validation`의 PR 제목은 `fix(auth): 토큰 검증 오류 수정`처럼 쓴다. `style`과 `revert`는 제목 유형으로만 허용되므로 현재 브랜치는 `chore/번호-요약` 또는 `fix/번호-요약` 등 허용된 유형을 선택한다.

### 12.8 자주 실패하는 예시와 해결

| 잘못된 예시 | 이유 | 수정 예시 |
| --- | --- | --- |
| `로그인 구현` | 제목 type과 콜론 없음 | `feat(auth): 로그인 구현` |
| `feat:로그인 구현` | 콜론 뒤 공백 없음 | `feat: 로그인 구현` |
| `feat(Auth): 로그인 구현` | scope 대문자 | `feat(auth): 로그인 구현` |
| `feature/42-login` | 지원하지 않는 브랜치 type | `feat/42-login` |
| `feat/login` | 이슈 번호 없음 | `feat/42-login` |
| `feat/042-login` | 이슈 번호 앞자리 0 | `feat/42-login` |
| `feat/42-JWT_login` | 대문자·밑줄 | `feat/42-jwt-login` |
| 브랜치 #42인데 본문 `Closes #43`만 있음 | 브랜치 번호와 불일치 | 실제 이슈 확인 후 `Closes #42` |
| `hotfix: 토큰 오류 수정` | 제목에 hotfix 미지원 | `fix(auth): 토큰 오류 수정` |

Conventions 실패는 PR의 Checks에서 실패 메시지를 확인한다. 제목·본문 오류는 PR에서 Edit하여 고치면 검사가 다시 실행된다. 브랜치명 오류는 올바른 브랜치에서 새 PR을 생성하고 기존 PR에 대체 PR을 연결한다. backend/ai 검사 실패는 해당 작업 로그에서 빌드·코드 검사·테스트 오류를 수정한 후 같은 작업 브랜치에 커밋을 추가한다. 필수 검사를 제거해서 통과시키지 않는다.

`Closes #번호`는 실제 완료하는 이슈에 사용하고, 작업이 남아 있으면 `Refs #번호`를 쓴다. GitHub의 자동 이슈 종료는 기본 브랜치로 머지될 때 적용되므로 일반 작업은 기본 브랜치 `dev`로 보낸다. 다른 레포 PR은 각 레포의 이슈를 완료하는지 별도로 확인한다.
